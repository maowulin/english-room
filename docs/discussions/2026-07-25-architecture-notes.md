# 多人英语实时语音房间架构讨论记录

日期：2026-07-25

状态：三仓架构已确认，TRTC 与评分细节待验证

## 题目目标

实现一条可以录屏演示的完整业务链路：

1. 多名玩家进入在线房间。
2. 玩家在房间内进行实时英语语音交流。
3. 系统获取或处理每名玩家的英语语音。
4. 房间结束后生成玩家口语评分。
5. 客户端展示评分结果及必要的局内表现信息。

建议开发周期为 3 天，最终主要交付物为 8—12 分钟 Demo 录屏和方案说明。

## 已确认的决策

### 客户端

使用 React Native Expo，以缩短 Demo 开发和多端调试时间。

### 后端

项目需要后端支持。后端至少需要承担以下职责：

- 生成腾讯云 TRTC 所需的安全凭证，避免将密钥放入客户端。
- 管理房间生命周期和玩家身份。
- 维护多人房间的成员状态。
- 触发并跟踪录制、语音处理和口语评分任务。
- 确保每段音频和评分结果能够关联到正确的玩家。

### 当前重点

真正的技术难点是多人同时在线和实时语音。基础框架应优先验证以下链路：

- 多名玩家能否稳定进入同一房间。
- 玩家加入、离开和掉线时，所有客户端看到的成员状态是否一致。
- TRTC 实时音频链路能否在 React Native Expo 开发方式下正常运行。
- 后端是否能够可靠地管理房间和玩家身份。

英语评分属于房间结束后的异步链路，应建立在多人房间和实时语音链路稳定的基础上。

## 已确认的架构原则

- 业务后端负责控制面，不直接转发实时音频流。
- 客户端通过腾讯云 TRTC SDK 传输实时音频。
- 腾讯云密钥只保存在后端。
- 房间内的实时成员事件与后端持久状态需要明确同步规则。
- 音频、录制文件、评分任务和玩家身份需要使用稳定 ID 关联。
- Demo 优先保证主链路清晰、可运行和可解释，避免过早引入微服务。

## 待讨论的问题

1. 如何获得每名玩家可用于评分的独立音频？
2. 评分任务的重试边界和幂等策略如何设计？
3. 本地 Demo 与录屏环境如何让多个客户端同时加入房间？
4. 腾讯云服务提供后，先验证 Android 还是 iOS 的 TRTC 原生集成？

## 讨论记录

### 2026-07-25

- 确认客户端使用 React Native Expo。
- 确认项目需要后端。
- 确认多人同时在线和实时语音是当前最高优先级。
- 决定先创建仓库，并在仓库中持续记录后续架构讨论。
- 确认采用 Monorepo，同时管理 Expo 客户端、FastAPI 后端和文档。
- 确认后端使用 Python FastAPI，不使用 Next.js 或 Node.js 后端。
- 确认 Expo 使用 Development Build/CNG，以支持后续 TRTC 原生模块。
- Demo 阶段使用单实例内存房间状态，通过接口隔离为后续 Redis 替换保留边界。
- 基础框架已在 iOS 模拟器完成原生构建，并打开可连接 FastAPI 的 Demo 页面。

### 2026-07-25：交付与运营架构更新

- 早期 Monorepo 决策只用于快速搭建基础框架，现被三仓架构取代。
- `english-room` 作为公开 App 仓库，也是候选人最终交付物。
- `english-room-backend` 作为私有 FastAPI 后端仓库，不随候选人交付。
- `english-room-op` 作为私有运营平台仓库，不随候选人交付。
- 正式 App 保留 Sentry、业务埋点和第一方事件上报能力。
- 运营页面、管理员权限、Sentry 查询 Token 和调试操作不进入正式 App。
- 内部运营包使用独立 App 变体和内部分发渠道，不把特殊入口隐藏在正式包中。
- Sentry 负责错误、性能、Session Replay、DAU、增长和核心转化指标。
- FastAPI 保存关键业务事件，用于精确计算 D1、D7、D30 留存和跨 Session 漏斗。
